# Алгоритм работы: антизалипание

Введено 04.10.2026 после трёх жалоб автора на скорость («Полчаса думаешь»,
«Тормозишь, аж бесишь», «Застрял. Поремонтируй себя»).
Файл читается перед каждой правкой документов пакета.

## Причина залипания (по факту, а не на словах)

1. **Чтение вместо действия.** Перед правкой я заново открывал файлы, которые
   уже прочитал в этом же разговоре. На одно решение уходило 3–5 проходов
   по `grep`/`sed` — это и есть потерянные полчаса.
2. **Цепочки проверок.** После правки я шёл проверять сумму, потом INCI,
   потом версию, потом счётчик шагов — четырьмя отдельными вызовами вместо
   одного.
3. **Меню вместо решения.** Я возвращал автору список «скажите а/б/в/г»
   там, где мог решить сам и дать право отменить. Это перекладывало мою
   работу на неё и удлиняло переписку.
4. **Длинные ответы.** Таблицы на пол-экрана там, где нужен был вывод.

## Правила

1. **Один запрос = максимум три вызова инструментов:**
   один проход чтения (все якоря сразу, одним `grep`/`sed`),
   один проход правки (весь пакет одним скриптом, `apply()` без прерывания),
   один остаточный контроль. Всё.
2. **Не перечитывать то, что уже читал в этом разговоре.** Память сессии —
   источник якорей. Если якорь не совпал — `apply()` печатает ПРОПУСК,
   я дописываю один точечный фикс, а не начинаю чтение заново.
3. **Не выносить решения на автора, если могу решить сам.** Решаю, вношу,
   сообщаю двумя фразами: что сделал и как отменить. Исключения — только то,
   что требует её данных или её денег: реквизиты, ОКПО, тип флакона и дозатора,
   публикация на сайте, запись в архив, закупка.
4. **Отчёт — не процесс.** Пишу результат: «внесено туда-то, сумма 100,00 %,
   открыто то-то». Не описываю, сколько проходов сделал.
5. **Ответ — до 20 строк.** Таблица только если её правда нельзя заменить
   тремя строками текста.
6. **Никогда не оставлять файл наполовину правленым.** Скрипт применяется
   целиком или не применяется вовсе; после него — один `grep` на остатки.
7. **Числа пересчитываю один раз, скриптом, и показываю только итог.**

## Проверка перед каждым ответом

- Сколько вызовов инструментов я сделал? Больше трёх — значит залип.
- Есть ли в ответе вопрос к автору, на который я мог ответить сам?
- Есть ли в ответе описание процесса вместо результата?

## Добавлено 06.10.2026 — после жалобы «зацикливаешься»
1. Не ждать обновления сайта в цикле (sleep до 2–3 минут выглядит как зависание). Выложить → проверить ОДИН раз → если ещё старое, написать «обновится через 1–2 минуты» и закончить.
2. Не повторять один и тот же ответ, если вопрос повторён. Повтор вопроса = прошлый ответ не подошёл → ответить иначе, прямо и коротко.
3. Не перекладывать работу на неё (скриншоты, проверки), если могу сделать сам. Если не могу — сказать прямо одной фразой.
4. Ответ закончен → сразу завершать. Не больше одного вопроса в конце, и только если без её решения нельзя.
5. Длинные задачи — делить: сначала короткий ответ, потом работа.

## Добавлено 02.11.2026 — клон без картинок (решение автора, «да»)

Причина: в архиве 89,9 МБ рабочего дерева, из них **80,7 МБ — картинки**
(43,9 МБ PNG, 24,7 МБ JPG, 12,1 МБ WebP) и 2,1 МБ шрифты. Тексты — 3,4 МБ.
Обычный `git clone` тянет 174 МБ за 5 секунд и провоцирует откат снапшота
воркспейса (предупреждение уже есть в `ПРОЧТИ_ПЕРВЫМ.md`). Ленивый клон без
картинок — 12 МБ за 1 секунду, содержимое то же.

1. Архив клонировать **только** так, иначе не клонировать вовсе:
   `git clone --depth 1 --filter=blob:none --sparse <repo> /tmp/arh`,
   затем `git sparse-checkout set --no-cone '/*' '!**/*.png' '!**/*.jpg' '!**/*.webp' '!**/*.svg' '!**/*.ttf'`.
   Сайт — так же с `'!images'` (77 МБ → 4 МБ).
2. Рабочая копия живёт в `/tmp`, в воркспейсе — только скрипт и то, что ждёт
   решения автора. Готовый скрипт: `clone_light.sh`.
3. Нужную картинку брать `git show HEAD:<путь> > /tmp/one.webp`, а не
   выкачивать папку.
4. **В ленивом клоне нельзя запускать `сохранить.py` и `манифест_целостности.py`:**
   они пересоберут манифест по неполному дереву и запишут хеши без картинок.
   Правки в манифест — только из полного клона.
5. Папку «картинки» внутри репозитория не создавать: перенос внутри Git размер
   не уменьшает, а ломает побайтовую сверку снимка и ссылки og/ленты.
