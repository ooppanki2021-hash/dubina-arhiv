### Когда робот реально обходил страницы

По `/indexing/samples` последний подтверждённый обход — **19 сентября, 14:00**:

- 17.09 — 1 страница
- 18.09 — 3 страницы
- **19.09 — 17 страниц** (всего 21, все HTTP 200)
- после 19.09 — **ни одной**

Три страницы, которые сейчас в поиске, имеют версии от 22.09. По документации,
после обхода робота данные в поиске обновляются **до двух недель**. Поэтому заявки
24.09 и 27.09 могли ещё не отразиться — но подтвердить это из API нельзя: раздел
«загруженные страницы» стоит на 19.09.

### Чем чреват частый переобход

Прямого запрета или штрафа за частоту Яндекс не публикует. Издержки другие:

1. **Квота уходит впустую.** Лимит — 150 URL в сутки. Отправляя весь сайт, тратите
   его на страницы, которые и так в поиске или не менялись.
2. **Переобход не лечит причину.** Если страница исключена как `LOW_QUALITY`, робот
   приходит, видит ту же страницу и принимает то же решение. Повторная заявка
   ничего не меняет — нужно менять содержание, а не повторять заявку.
3. **Статус `DONE` — это не «попал в поиске».** Это только «робот обошёл». Данные
   в поиске обновляются до двух недель. Легко принять `DONE` за успех.
4. **Полный переобход по sitemap — не чаще раза в месяц.** До 28.09 сделано две
   партии почти целиком за четыре дня.
5. **Часть файлов отправлять бессмысленно:** `robots.txt` переобходится сам за
   несколько часов, XML-фиды и sitemap — не гарантированно, favicon — через главную.
6. **Обход по счётчику Метрики** — отдельный инструмент для больших объёмов, когда
   лимита переобхода не хватает.

## 6. Какую версию страницы увидит робот

**Заявка на переобход — не снимок страницы, а приглашение прийти.** Робот читает то,
что лежит на странице в момент его прихода. Поэтому:

- правки опубликованы **до** прихода робота → увидит новую версию;
- правки опубликованы **после** прихода робота → увидит старую, и новые он не видел.

### Что было по факту

Заявка 27.09 ушла в **21:59**. Задача добавлена в 21:59 и имеет статус `DONE` —
значит робот приходил **после** 21:59. Это точно. Неизвестно только, до или после
22:47. Окно, в котором он мог пропустить последние правки, — **48 минут**.

### Почему 8, а не все 25

Возражение автора было верным: **редактировались все 29 страниц, и картинки новые
на 25 из них.** Но распределение по времени такое:

| Этап работ | Время | Относительно заявки 21:59 |
|---|---|---|
| Иллюстрации, все страницы | 14:19 – 18:42 | **до** — робот видел |
| Переименование бренда, иконки | 26.09 | **до** |
| Мобильная триада, таблицы, схемы | 27.09 21:01 – 21:11 | **до** |
| Редактура текста, орфография | 27.09 21:42 – 21:47 | **до** |
| Блоки перелинковки 1–5, OG | 27.09 22:03 – 22:47 | **после** — робот мог не увидеть |

То есть всё визуальное (картинки) и большая часть правок опубликованы **до** заявки.
После заявки шла **перелинковка** — блоки 1–5, которые связывают страницы между собой.
Для SEO это важнее картинок: перелинковка передаёт вес и помогает роботу находить
страницы. Поэтому отправлены именно эти 8.

### Почему не отправлены две служебные страницы

`/politika-konfidencialnosti/` и `/soglasie-na-obrabotku/` тоже менялись 27.09,
но по диффам:

- `f34129c` (21:11) — текст ссылки в меню: «Общая карта» → «Протокол зачистки»;
- `25e3a59` (22:03) — добавлены OG-метатеги.

**Юридический текст не менялся ни на символ.** Ни даты, ни условий, ни состава
обрабатываемых данных. OG-теги на закрытой странице бесполезны: они нужны, когда
ссылкой делятся в соцсетях, а политику конфиденциальности никто не расшаривает.

Роботу там нечего нового читать. К тому же эти страницы:

- `noindex, follow` — в поиске не нужны и не появятся;
- отсутствуют в sitemap намеренно: sitemap говорит «вот важные страницы, прошу
  индексировать», и служебная страница с `noindex` там даёт противоречивый сигнал;
- обе отдают HTTP 200 и ссылки на них есть на 27 страницах — робот найдёт их сам.

Страницы **обязательны по закону и на месте** — речь шла только об очереди переобхода,
не об их нужности. Если захочется страховки на случай, если робот к ним не заходил,
это ещё 2 URL из 150 — но содержательной причины нет.

## 9. Почему так и что с этим делать

Сайту около месяца (первый коммит — 25.09.2026). Яндекс молодым сайтам доверяет
осторожно, а внешних ссылок почти нет — поэтому страницы снимаются как

Порядок действий по силе воздействия:

1. **Внешние ссылки** — самый сильный рычаг. Сейчас по ссылкам приходит 21 визит.
2. **Довести до сути тонкие страницы** — `/karta-osetii/`, `/o-proekte/`,

   Переобход тут не поможет — нужно содержание.
3. **Переобход** — только по изменённым страницам и с честным `lastmod`.
4. **Яндекс.Справочник** — единственная рекомендация Вебмастера. Карточка
   организации — доверенный сигнал и повод для упоминаний.
5. **Время** — обычно 1–3 месяца. Это нормальный срок, не поломка.

## 10. ПРАВИЛА ДЛЯ ПОМОЩНИКОВ: переобход и sitemap

Этот раздел — рабочая инструкция, чтобы не повторять ошибок.

### Переобход страниц

| Параметр | Значение |
|---|---|
| Дневная квота | 150 URL (индивидуальна, зависит от качества сайта) |
| Обработка заявки | до 3 суток |
| Обновление данных в поиске | до 2 недель |
| Полный переобход по sitemap | **не чаще 1 раза в месяц** |
| Проверка квоты | `GET .../recrawl/quota` |
| Список задач | `GET .../recrawl/queue` |

**Что отправлять:**
- новые страницы — сразу после публикации;
- страницы с **реальными содержательными** правками;
- страницы, которые были исправлены после исключения — и то только если содержание
  изменилось по существу, а не косметика.

**Что НЕ отправлять:**
- страницы, которые не менялись — робот подберёт их по sitemap;
- страницы, уже находящиеся в поиске, если они не менялись;
- страницы, исключённые как `LOW_QUALITY`, **если содержание не менялось** —
  робот придёт, увидит то же самое и примет то же решение;
- служебные страницы с `noindex` — в поиске им не быть, робот найдёт их по ссылкам;
- `robots.txt` (переобходится сам за часы);
- XML-фиды и `sitemap.xml` (переобход не гарантируется);
- `favicon.ico` (через главную страницу).

**Как отправлять:**
- порциями по изменённым страницам, а не весь сайт залпом;
- **сначала** правка → **потом** обновление `lastmod` → **потом** заявка;
- перед отправкой сверить квоту, чтобы не уйти в минус;
- после отправки проверять не `DONE`, а изменение числа страниц в поиске —
  `DONE` означает только «робот обходил».

### Sitemap

- `lastmod` должен указывать **реальную дату последнего изменения** страницы.
- Завышать `lastmod` без изменений нельзя: робот перестаёт верить файлу.
- Меняется одна страница — меняется `lastmod` у неё одной, не у всех.
- Служебные страницы с `noindex` в sitemap не держать: сигнал противоречивый.
- Файл перечитывается Яндексом сам; гнать его на переобход не нужно.

### Инструмент

```
python3 /home/user/webmaster_recrawl.py --urls /,/faq/,/kviz/    # выбранные страницы
python3 /home/user/webmaster_recrawl.py --urls spisok.txt        # список из файла
python3 /home/user/webmaster_recrawl.py --since 2026-09-27       # у кого lastmod свежее даты
python3 /home/user/webmaster_recrawl.py --urls /,/faq/ --send    # реально отправить
```

Без `--send` скрипт только предлагает и ничего не шлёт. Эндпоинты для контроля:
`/recrawl/quota`, `/recrawl/queue`, `/indexing/samples`,
`/search-urls/in-search/samples`, `/search-urls/events/samples`.

### Что считать успехом

Не количество отправленных заявок и не `DONE`, а:

- рост `searchable_pages_count`;
- рост числа поисковых запросов с показами;
- рост визитов из поиска в Метрике.

## 12. Вебмастер: два сайта оказались одним

В Вебмастере было две записи. Это не два сайта, а один сайт на двух протоколах:

| Запись | Что внутри |
|---|---|
